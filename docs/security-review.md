# Main 보안 수정 및 검증

기준은 `main`의 `025dad569f2ba061ce0531c543d7a22a556d38fb`입니다. 사용자의 최신 브랜치 지시에 따라 기존 main의 보안 경계를 수정했습니다. contributor의 순위·압축·업적 기능은 추가하지 않았습니다. 이전 contributor PR #12는 이미 병합된 상태로 보존했습니다.

## 수정한 문제

- 인증 없는 내부 Go API의 owner 식별자 위조: loopback 수신, 프로세스별 난수 토큰 확인, 실행 전 바이너리 해시 검증을 적용했습니다.
- 제한 관리자의 임의 계정 필드 접근: 필요한 프로필 필드만 허용하고 권한·비밀번호·복구 키 등은 거부합니다.
- 비공개 원문·역사·차이·편집 불러오기·include·인물 템플릿 인자 노출: canonical ACL 및 개인정보 경계를 적용하고 오류는 거부합니다.
- DB 안의 세션 서명키와 평문 복구 키: DB 외부 32바이트 키에서 세션 서명을 파생하고 복구 키는 HMAC 검증값으로 이관합니다. 비밀번호 hash/salt는 보존합니다.
- 로그인·리로·회원가입·2FA 인증 상태: 600초 수명과 목적·계정 결합을 적용하고 세션 잔여 상태를 지웁니다. 복구는 원자적으로 한 번만 성공하며 회원가입 오류는 rollback합니다.
- CSRF·스킨 경로·SVG·응답 헤더·난수 생성도 보강했습니다. 익명 프로필 API는 401이며 UI는 이전 개인정보를 지웁니다.

일반 회원의 제목 검색은 유지되지만 본문 검색은 canonical ACL override 권한에 제한됩니다. 이는 비공개 본문 검색 결과를 통한 유출을 막기 위한 동작 변경입니다. 기존 main의 인기 문서 API, 사이드바, 대용량 문서 폼 제한은 유지했습니다.

첨부에서 언급한 압축/checkpoint/native ranking 문제는 현재 main에 해당 구현이 없으므로 이 커밋의 수정 대상이 아닙니다. contributor에서는 PR #12로 별도 보강했습니다. 고의적인 백도어라는 근거는 확인하지 못했습니다.

## 실제 검증

- Windows Python 3.13.12 및 Linux Python 3.12.3: 각각 103개 실행, 102개 통과, 실제 MySQL 서버가 필요한 검사 1개 제외.
- 기존 표준 unittest 실행 방식을 보존했습니다. Python compileall, Node 수식 렌더러와 프로필 UI 검사, 최종 Git diff 공백 검사를 통과했습니다.
- 실제 Flask + 인증된 Go + 격리 SQLite에서 DB-only owner 쿠키 위조 거부, 로그인/2FA/복구, 기존 키 이관, 1회 복구, 제한 관리자 필드 거부, CSRF 및 비공개 raw/include/검색 거부를 확인했습니다. 정상 owner 접근과 기존 익명 인기 문서 API도 유지됩니다.
- Go 소스·overlay·manifest 및 5개 실행 파일은 앞서 독립 검토·go vet·180개 ACL 전후 비교가 통과한 소스와 바이트가 동일합니다. 이번 main 앱 연결은 Windows amd64와 Linux amd64에서 실행했습니다. 나머지 플랫폼은 교차 빌드 및 해시 확인 범위입니다.
- 새 런타임 의존성, 순위 작업, 상시 타이머, 전역 문서 캐시는 추가하지 않았습니다. 공개 include의 추가 ACL RPC는 0회이며 제한 문서는 요청당 같은 제목에 한 번 확인합니다. 공개 페이지의 권한 확인 원문을 재사용해 중복 호출과 description SQL을 제거했습니다.

## 원본 main 대비 성능

동일한 새 SQLite fixture(문서 20,000개, view ACL 1,000개), 3번의 순서 교대, 흐름별 버전당 150회 요청으로 비교했습니다. 요청 제한과 권한 검사는 켜져 있으며 배치 사이에서만 fixture 제한 상태를 초기화합니다. 아래는 실행별 중앙값입니다. p50 및 Python CPU 단위는 ms, RSS는 Python+Go의 정지 상태 합계 MiB입니다.

## 서버 설치와 키 보관

서버에 Go 컴파일러를 설치할 필요는 없습니다. 해당 OS/CPU의 보안 실행 파일과 `route_go/security/manifest.json`을 저장소 루트에 함께 배치하고 `python3 app.py`(Windows는 `python app.py`)로 실행합니다. Linux는 실행 파일에 실행 권한을 줍니다. 제공된 `main-secure-backend-*.zip`은 이 구조와 라이선스를 포함하며 파일 해시와 압축 무결성을 검증했습니다.

직접 빌드할 컴퓨터에는 Python 3.11+ 및 Go 1.24.1+가 필요합니다: `python route_go/security/build_backend.py --target linux-amd64`. Docker는 빌드 단계에서 Go를 사용하고 실행 이미지에 Go를 넣지 않습니다. 기존 인증 없는 upstream 바이너리로 되돌리면 시작 검증을 통과하지 않습니다.

`app_session/security.key`는 Go 빌드가 아니라 새 Python 앱 시작 때 자동 생성합니다. 영속 보관하고 DB와 함께 안전하게 백업하세요. Git/공개 저장소에 넣지 않습니다. `NAMU_SECURITY_KEY_FILE`로 경로를 지정할 수 있으며 여러 프로세스는 같은 키를 사용해야 합니다. 키를 잃으면 기존 세션과 복구 검증값을 재사용할 수 없습니다. 기존 사용자 원문 복구 키는 정상 이관 후 계속 사용할 수 있습니다.

## 방어 범위

DB 전체 쓰기 권한으로 원본 관리자 테이블이나 이력을 직접 수정하는 공격, 앱 파일/키/프로세스 환경 유출, 기존 비밀번호 hash의 offline cracking, 과거 DB 백업에 남은 평문 복구 키는 이 변경만으로 해결되지 않습니다. 이전 DB 유출이 의심되면 복구 키를 재발급해야 합니다. 운영 DB 및 실제 인증 서버에 접근하거나 운영 배포를 수행하지 않았습니다.

변경 범위는 원본 clean main과 명시적인 파일 경로로 확인하며 기존 gitlink를 보존합니다. native 실행 관리 도구는 workspace 경로 처리 오류로 시작하지 못했으므로 정식 승인 receipt를 주장하지 않습니다. 실제 Git·파일 해시·실행 결과와 독립 소스 검토로 검증합니다.

최종 p50 관측에서 증가한 흐름: 없음. 운영 전체의 성능 불변은 별도 검증이 필요합니다.
